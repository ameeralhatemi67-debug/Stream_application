### Why the concurrent test proves H1/H2

`brief/tools/broadcast_session_concurrency.mjs` uses separate `psql` processes in the named disposable database container. It holds the common writer lock, starts End on another connection, and queries `pg_stat_activity` until End is observably waiting on an advisory lock. The lock holder replaces the session and commits. Before repair, both cases report `live:false`, watch null and session ended. After repair, the replacement remains live. The same-watch case explicitly ends and starts a new session while holding the lock; comparing only the watch ID would not pass this case safely.

The expiry test separately holds the writer/profile lock, lets the old sweep take its snapshot and block on the row, renews/starts, then commits. Before repair the replacement ends. After repair the sweep refuses the busy writer lock before selecting, leaving the replacement live. This is synchronization through observed database waits, not a sleep-only stress test. Cleanup warnings about rollback outside a transaction are harmless and retained in the transcript.

### Group boundaries checked

**Group 1.** Public room identity is the current exact watch ID, not a sample/fallback channel. Session IDs are authorization-scoped by owner/device RPC checks; public visibility of a session ID is not a capability to end it. Transfer ends the previous broadcast, preserves the appropriate device ownership rules, and the new primary must start deliberately. Admin Hide/Show changes discovery only. End stops the app session without demoting the broadcaster; End-and-block also blocks relisting that watch ID. These actions do not end a YouTube broadcast or stop OBS. A connected app phone is told to stop; a disconnected phone cannot receive that instruction immediately. The public catalog's lease/polling bounds are not an instant push guarantee.

The unique live-watch index refutes the claim that two accounts can concurrently list one watch ID through normal writers: the regression gets 23505. Reuse after End is allowed. The stale-organization cross-account case was real and is now scoped to session ownership. The separate REST/Realtime probe verifies that owner/admin profile events arrive, but unrelated viewer events do not under RLS. Rooms must use their 20-second reads and feed/map freshness bounds; E4 must measure perceived convergence and network loss.

Event delivery was not uniform across runs. After restarting the local stack, the receiving owner's event was absent at 10 seconds even though admin events and direct state reads succeeded. An unchanged warm repeat passed all 19 checks with that event arriving in 23 ms. Both transcripts are retained; the cause of the missed event is unproven. Transfer already performs an explicit catalog read, and broadcasting clients check remote End during their 20-second heartbeat. This is a reason to retain polling and require physical latency evidence, not to promise reliable instant Realtime delivery.

**Group 2.** Lookup checks existence/current scheduling/channel metadata, not live audiovisual content. Phone, OBS-on-computer and another-phone-app are separate sender modes. The external routes never copy a stream key and never claim encoder telemetry they lack. The key/watch swap checks and account-scoped Find operation are covered. A scheduled broadcast within one hour remains allowed so a phone can prepare ingest; that is explicitly **not** evidence that a viewer can play it now. E4 should record scheduled and live cases separately.

**Group 3.** New widget tests exercise the screen's reaction to remote End and rejected ingest, not just an engine mock in isolation. Native source inspection finds **RtmpCamera2**, GL `muteVideo()`, and a no-op `handleSetOrientation`. This contradicts older STATUS/AGENTS statements describing a completed RtmpStream source-swap migration; those dirty owner documents were preserved. A foreground notification service exists, but capture is still owned by the bridge/view lifecycle. It is inaccurate to call service-owned background broadcasting complete, or to say there is no service at all. Leaving the screen ends after confirmation; Home/lock survival is unaccepted. Audio-only currently hides video while the camera stays open.

**Group 4.** Local shows unavailable and asks for no IP, saves no endpoint and starts no camera. The former laptop-IP administration field and misleading instructions are gone. Unreachable `localRtmp`/WebLivePlayerAdapter remain as cleanup debt, not a working LAN receiver. Private internet streaming remains disabled; hidden/unlisted does not mean authenticated private media. Laptop in-app capture and Local transport require separate implementation decisions.

**Group 5.** Native command acknowledgement means dispatch only; onStateChange and observed mute drive UI truth. Unsupported rendition commands are no longer offered. The supported YouTube SDK owns cross-window messaging; the application no longer trusts raw message payloads based on a substring origin check. Its wrapper checks the exact player callback target and a four-command allowlist. The VM regression executes the generated HTML's actual script with an SDK stub, so it proves our wrapper, not Google's internals or native WebView behavior. The navigation allowlist and ADR-006 privacy embed/base/referrer stay intact.

Retry recreates the room player with its known mute choice. One keyed player is retained through mocked rotation/fullscreen changes. Chrome's adapter probe verifies actual iframe creation, watch replacement, controls and remount; it does not verify a whole authenticated room, physical Android retention, audible mute or a phone-to-viewer nonce. Chrome's built-in mute is not synchronized to Flutter, so cross-Retry mute retention on Chrome is not claimed. The return chip says playback stopped; it is not a mini-player or PiP. Native Windows viewing was not runtime-tested and should use the supported Chrome path for this acceptance run.

## Watch-link policy and bypass boundary

**Both demo and release fail closed in the shipped client.** Missing API key, outage/quota/timeout, missing approved channel or failed channel resolution prevents listing and prevents starting the phone flow. The UI explains the refusal and allows retry after configuration/network recovery. There is no hidden demo bypass and no automatic verified label on an unchecked link. Tests with synthetic API responses are development evidence only.

Successful checks mean “YouTube metadata matched the channel recorded on the approved application/organization at lookup time.” They do not prove OAuth ownership, who holds the ingest key, that this encoder is bound to that watch ID, embedding availability on a particular viewer, audio/video delivery, future availability, or privacy. Metadata can change after lookup.

**A modified client can bypass all watch-link checks.** The database still accepts a syntactically valid ID from an approved, primary-device account, subject to organization permissions, moderation blocks and live-watch uniqueness. It does not call YouTube, prove Google channel ownership or bind RTMP ingest to the listed video. D8 is absent. A server public-metadata check could be added without OAuth, but authenticated create/bind/start/end and strong channel authorization require the coordinator/OAuth work. Do not market the current backend as enforcing verified YouTube playback. This supersedes the fail-open text in Opus's historical OWNER_DECISIONS and REPORT.

## SQL permissions and migration compatibility

All migration history was applied from scratch to a separate local PostgreSQL 17/Supabase stack, then the complete SQL suite was independently executed. The two repairs are **new timestamped migrations**; historical migrations were not edited. Replaced definer functions retain empty search paths and their existing ACLs; End explicitly revokes public/anon and grants authenticated execution. Table writes stay server-only, owner/admin history reads stay RLS-filtered, and wrong-account/anon/moderation denial cases run in the SQL suite.

Gate informational items were reviewed: `stream_viewers` and `removed_live_streams` intentionally have deny-all direct access, through bounded definer helpers/guards instead. The three anonymous executable helpers are public chat sender projection, viewer heartbeat and viewer counts; they do not grant broadcast control. Public views intentionally expose discovery/ingest metadata and are not a privacy boundary.

**Rollout constraint:** the original Opus migration backfills an already-live session's organization by matching watch ID. A stale legacy org row can make that inference ambiguous. Fresh-install testing does not establish a safe hot upgrade with ongoing broadcasts. Before any separately authorized staging/release migration, quiesce all live profiles/organizations, exclude older app builds, inspect legacy flags and apply all three migrations together. This audit did not perform a hosted hot migration. Legacy clients can still call `set_live_state`; new clients refuse a missing session RPC. An old client without a session token cannot gain the new End guarantee merely by installing SQL. Minimum-version rollout and a preflight are release work, not implied by this source merge.

## Current primary documentation consulted

Consulted through Context7 and official sources on 2026-09-26; installed package code was also inspected where the web behavior depended on its implementation.

- PostgreSQL Read Committed commands obtain snapshots per command, and explicit locks must precede the read whose consistency they protect: [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [application consistency](https://www.postgresql.org/docs/17/applevel-consistency.html), [advisory lock functions](https://www.postgresql.org/docs/17/functions-admin.html). The live three-connection test establishes applicability here.
- YouTube supports binding `YT.Player` to an existing iframe with enablejsapi, onReady/state events and the hosting-page origin: [IFrame Player API](https://developers.google.com/youtube/iframe_api_reference), [player support](https://developers.google.com/youtube/players/support). [Revision history](https://developers.google.com/youtube/iframe_api_revision_history) explains removal of playback-quality setting. A 320px-wide 16:9 viewport can fall below YouTube's documented 200px minimum height; narrow-screen physical usability remains an E4 limitation.
- Arbitrary cross-window messages require exact source/origin validation: [MDN postMessage security guidance](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage). Using the SDK removes the application's weak raw-message receiver; the stub test does not audit SDK internals.
- Local reset/test behavior: [Supabase CLI reference](https://github.com/supabase/cli/blob/develop/apps/cli/docs/go-cli-reference.md), [database test command](https://github.com/supabase/cli/blob/develop/apps/cli/docs/supabase/test/db.md). Commands named the isolated workdir and used `--local`; none used `--linked`.
- Android camera/microphone foreground-service permissions and background-start limits: [service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [background restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). A notification service and a passing APK build do not prove capture survival on a physical phone.
- Installed `youtube_player_iframe_web` 3.1.3 registers `WebViewPlatform` and its `loadRequest` sets iframe.src. The suspected “missing Chrome backend” was therefore refuted; the reproduced defect was the app's loading-cover lifecycle. [Package source](https://github.com/sarbagyastha/youtube_player_flutter/tree/develop/packages/youtube_player_iframe_web) is the upstream reference; the installed version and real browser probe are the evidence used.
