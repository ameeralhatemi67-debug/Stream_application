# v0.9 — Settings Cleanup, Account Deletion & Consent/Legal

**Why this version exists:** "Cleaning up the settings," plus the audit's account-deletion and PDPL-consent findings (both hard store-submission blockers per `doc/Audit/03_Saudi_Legal_And_Store_Compliance_Audit.md`). Your own framing: the toggles currently in Settings that are really "experimental/testing" controls now belong in the Admin surfaces built in v0.8, not in front of every user — but that doesn't mean every remaining user sees the same settings. A Viewer's settings are a baseline; Streamer, Org Owner, and Admin each see additional sections layered on top, driven by the real roles from v0.5/v0.8.

**Depends on:** v0.8 (role data drives which settings sections render).

## Checkpoint 1 — Settings Information Architecture

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Remove Experimental Toggles from User-Facing Settings
- Audit every toggle currently in `settings_screen.dart` (73KB — the UX audit already flagged this file as sprawling); anything that's really a testing/dev/pitch-director control (e.g. the Pitch Director mock-override mode from ADR-005) moves into an Admin-only settings surface, reachable from the v0.8 Admin Hub, not the general Settings screen.
- **Commit:** `refactor(settings): move experimental/dev toggles to Admin-only surface`

### Phase 2: Role-Aware Sections
- Restructure `settings_screen.dart` so sections render conditionally based on the user's real role from v0.5/v0.8: Viewer sees the baseline (profile, notifications, language/theme, privacy); Streamer additionally sees streaming preferences/quality defaults; Org Owner/Co-Owner additionally sees org-management shortcuts; Admin/Master Admin additionally sees a link into the Admin Hub.
- **Commit:** `feat(settings): role-aware settings sections`

### Phase 3: Visual/Layout Consolidation
- Address the UX audit's layout findings for this screen: card spacing, typography hierarchy, touch-target sizing — this is the "polish" work for this version, landing here rather than in a separate polish version.
- **Commit:** `polish(settings): layout, typography, and touch-target consolidation`

## Checkpoint 2 — Account & Data Deletion

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: In-App Deletion Flow
- "Delete My Account" in Settings → confirms intent, then deletes the Supabase Auth user and cascades (deletes or anonymizes, per what the data actually needs to remain for audit-log integrity) their related rows across `profiles`, `broadcaster_applications`, `chat_messages`, etc.
- **Commit:** `feat(settings): in-app account and data deletion`

### Phase 2: Hosted Web Deletion Request Page
- A simple static page (doesn't need to be part of the Flutter app) users can reach without the app installed, satisfying Google Play's account-deletion policy requirement for a web path.
- **Commit:** `feat(legal): hosted account-deletion request page`

## Checkpoint 3 — Consent & Legal

**🚀 Checkpoint kickoff:** push to GitHub.
**🧹 Optional polish session:** worth a fresh-eyes read-through of the actual consent copy (Arabic and English) before calling this done — legal copy is exactly the kind of thing worth a second look outside the build-and-ship rhythm.

### Phase 1: Onboarding Consent Step
- A distinct step (not the full product-tour onboarding, which lands in v1.0) capturing explicit, recorded consent to data collection/privacy terms before any personal data is gathered — for both Google sign-in and guest flows. This is the PDPL gap from Phase 3 of the audit.
- **Commit:** `feat(legal): onboarding consent step with recorded acceptance`

### Phase 2: Data Export
- "Download my data" — a basic export of the requesting user's own stored data (profile, application, chat history if retained) as a PDPL data-portability mechanism.
- **Commit:** `feat(legal): user data export`
