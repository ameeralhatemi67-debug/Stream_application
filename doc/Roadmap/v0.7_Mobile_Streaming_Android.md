# v0.7 — Mobile Streaming, Android (Video + Audio-Only)

**Why this version exists:** "adding the ability to stream from phone, stream and audio-only. for web keep the OBS stream connection." Today, "Go Live" only works via YouTube Live linking or a local OBS/RTMP connection meant for testing — nothing captures the phone's own camera/mic and pushes it anywhere. This version builds that, **Android only** — iOS's version of this feature ships inside v1.1 so it's built once per platform, at the point each platform is actually being finished, rather than twice.

**Depends on:** v0.5 (auth/roles for who's allowed to go live).

> **🛠️ Recommended Skills for v0.7:**
> - `claude-flutter-skill` (`Arcturus91/claude-flutter-skill` — Flutter camera, audio lifecycle, foreground services)

## Checkpoint 1 — Research & Library Spike

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Evaluate RTMP Publishing Approaches
- Flutter has no first-party camera-to-RTMP encoder — survey current options: a maintained pub.dev RTMP-publisher package vs. a custom platform-channel wrapper around a native Android RTMP library. Confirm the winner still targets a current Android/NDK toolchain and doesn't conflict with `flutter_vlc_player`'s native dependencies already in the project.
- Build a throwaway prototype: phone camera + mic → RTMP → a test YouTube stream, confirming actual end-to-end latency and stability before committing to the approach in the rest of this version.
- **Commit:** `spike(streaming): prototype phone camera/mic to RTMP publishing`

---

## Checkpoint 2 — Go Live From Phone (Video)

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Permissions & Capture
- Add `CAMERA` and `RECORD_AUDIO` back to `AndroidManifest.xml` (removed in the audit specifically because nothing used them yet — this is the feature that justifies them) with proper runtime-permission rationale dialogs, shown contextually right before the OS prompt.
- Add `FOREGROUND_SERVICE` + a properly typed media/camera foreground service so a broadcast survives backgrounding/screen-lock, closing the gap Phase 2 of the audit flagged as unverified.
- Camera preview screen with front/back swap.
- **Commit:** `feat(streaming): camera/mic capture and permissions for phone broadcasting`

### Phase 2: RTMP Target Entry
- Extend the existing `rtmp_ip_dialog.dart` pattern (currently local-OBS-only) with a "Stream to YouTube" mode: manual paste of the RTMP URL + stream key from YouTube Studio (per the agreed manual-first approach).
- **Commit:** `feat(streaming): manual YouTube RTMP key entry for phone broadcasting`

### Phase 3: Go-Live Controls
- Start/stop broadcasting, mic mute, camera swap mid-stream, basic resolution/bitrate presets (matching device capability — don't default to a setting that saturates a mid-tier phone's upload bandwidth).
- **Commit:** `feat(streaming): go-live controls for phone video broadcasting`

## Checkpoint 3 — Audio-Only From Phone

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Mic-Only Capture
- Reuse Checkpoint 2's RTMP pipeline in audio-only mode (mic capture, no camera), paired with a static thumbnail/background image for the YouTube stream (YouTube requires a video track even for "audio-only" content).
- **Commit:** `feat(streaming): audio-only phone broadcasting`

### Phase 2: Background Broadcasting
- Confirm audio-only broadcasts survive the phone being locked/backgrounded, using the same foreground-service work from Checkpoint 2.
- **Commit:** `feat(streaming): background-safe audio-only broadcasting`
