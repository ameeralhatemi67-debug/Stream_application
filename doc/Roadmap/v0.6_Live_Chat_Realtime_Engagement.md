# v0.6 — Live Chat & Realtime Engagement

**Why this version exists:** "have the chat option work and is live between all people in that stream" — today's `live_chat_widget.dart` has no real multi-user backend at all. This version replaces it with Supabase Realtime, and builds moderation in from the start rather than retrofitting it (the audit's Apple Guideline 1.2 finding).

**Depends on:** v0.5 (needs the Supabase project, auth, and RLS pattern already in place).

> **🛠️ Recommended Skills for v0.6:**
> - `supabase/agent-skills` (Supabase Realtime broadcast channels and PostgreSQL presence)
> - `claude-flutter-skill` (`Arcturus91/claude-flutter-skill` — efficient chat list rendering and scroll controllers)
> - `appstore-review-skill` (`devsemih/appstore-review-skill` — Apple Guideline 1.2 User-Generated Content / moderation compliance)
> *(If any skill is not installed, prompt the user or load it before execution).*

## Checkpoint 1 — Realtime Chat Core

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Schema & Channel Design
- Add a `chat_messages` table (stream_id, sender_id, body, created_at) with RLS: any authenticated participant of a stream can read; a sender can only insert as themselves.
- Design the Supabase Realtime broadcast-channel naming convention (one channel per `stream_id`).
- **Commit:** `feat(chat): chat_messages schema and RLS`

### Phase 2: Replace the Simulated Chat Engine
- Wire `live_chat_widget.dart` to subscribe to the stream's Realtime channel and to Postgres inserts on `chat_messages`, replacing whatever currently drives the visible message list.
- Keep the existing ghost/simulated commentary engine (`ghost_comments.dart`) as an explicit fallback path (see Checkpoint 4), not deleted.
- **Commit:** `feat(chat): live chat backed by Supabase Realtime`

### Phase 3: Send/Receive UX
- Message send with optimistic UI update + real delivery confirmation; connection-state indicator (connecting/live/reconnecting) so a dropped Realtime connection is visible to the user rather than silently going stale.
- **Commit:** `feat(chat): message send UX and connection-state indicator`

## Checkpoint 2 — Reactions & Role Badges

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Floating Emoji Reactions over Realtime
- Send reactions (❤️ 👏 🔥) as ephemeral Realtime broadcast events (not persisted to Postgres — no reason to store millions of reaction rows against the free tier's message quota).
- Wire into the existing `floating_emoji_overlay.dart`/`floating_reactions_overlay.dart` widgets, replacing whatever currently triggers them locally-only.
- **Commit:** `feat(chat): realtime floating emoji reactions`

### Phase 2: Role Badges in Chat
- Render a badge next to each sender's name based on their `user_roles` row from v0.5/v0.8's schema: 🎙️ Speaker, 🏛️ Organization, 🛡️ Admin, ✅ Verified.
- **Commit:** `feat(chat): role badges in chat messages`

## Checkpoint 3 — Moderation

**🚀 Checkpoint kickoff:** push to GitHub.
**🧹 Optional polish session:** good point for a dedicated adversarial pass — try to break moderation as an unprivileged user before calling this checkpoint done.

### Phase 1: Report & Block
- "Report message" action → writes to a `chat_reports` table (visible to admin tiers).
- "Block user" — client-side hide of future messages from that sender for the blocking viewer, stored per-user (not a platform-wide action).
- **Commit:** `feat(chat): report message and block user`

### Phase 2: Streamer/Admin Moderation Controls
- Mute/delete-message actions available to the stream's owner and admin tiers, **enforced by RLS + a Supabase Edge Function**, not just a client-side check — this is the one place where "moderation" must not repeat the client-trust mistake from before.
- **Commit:** `feat(chat): streamer/admin mute and delete-message controls, server-enforced`

### Phase 3: Basic Keyword Filter
- A simple server-side keyword/profanity filter on insert (Edge Function or Postgres trigger) as a first line of defense — not a substitute for report/block, but closes the gap Apple's Guideline 1.2 review specifically looks for ("active safety controls," not just after-the-fact reporting).
- **Commit:** `feat(chat): basic keyword filter on message insert`

---

## Checkpoint 4 — Offline/Fallback Handling

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Ghost Chat as Explicit Fallback
- When Realtime is unreachable (offline testing, connection drop), fall back to the existing simulated ghost-chat engine with a visible "demo mode" indicator, so it's never presented as if it were live traffic.
- **Commit:** `feat(chat): ghost-chat fallback for offline/disconnected state`

---

**End of v0.6.** Chat is now real, works between everyone in a stream, has reactions and role badges, and — unlike most of the rest of the app before this roadmap — has moderation that's actually enforced server-side from day one.
