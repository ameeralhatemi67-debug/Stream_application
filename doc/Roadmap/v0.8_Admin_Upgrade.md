# v0.8 — Admin Upgrade (Tiered RBAC) ✅ Complete (2026-08-23)

**Why this version exists:** "Upgrading the admins" — replacing the flat "3 hardcoded emails = super admin" model with a real hierarchy, now that v0.5 gives us a real backend to enforce it and v0.6 gives admins something new to moderate.

**The hierarchy, as you specified it:**
1. **Master Admin** — top tier. Can grant the Master Admin role to others (so there can be multiple Master Admins — this is the "goes back to where I work" case, e.g. co-founders/trusted leads). Unrestricted platform control.
2. **Admin** — appointed by a Master Admin. Day-to-day moderation/verification powers; cannot grant Master Admin or Admin roles to others (only a Master Admin can).
3. **Permitted Admin** — for Organization Owners and Co-Owners specifically. Scoped to their own organization only, not platform-wide.
4. **Checkbox-style granular grants** — layered on top of any tier above: a Master Admin (or an Admin, if permitted to) can tick specific extra capability checkboxes for a given user, independent of their base tier (e.g. "can also edit platform Terms & Conditions" for a specific Admin who wouldn't otherwise have that).

**Depends on:** v0.5 (the `user_roles`/`user_permissions` tables were already scaffolded there specifically so this version doesn't need another schema migration round).

## Checkpoint 1 — Roles & Permissions Data Model ✅ Complete (2026-08-23)

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Role Hierarchy Schema
- Finalize the `user_roles` table: `role` enum (`master_admin`, `admin`, `permitted_admin`, `user`), `granted_by` (references the granting user, for audit trail), `org_id` (nullable — only set for `permitted_admin`, scoping it to one organization).
- RLS: a `master_admin` can insert/update any row; an `admin` can only insert/update rows for `user`-tier accounts (i.e. can't self-promote or promote others to admin/master_admin); `permitted_admin` rows can only be set by a `master_admin`/`admin` or derived automatically from organization ownership (see Phase 3).
- **Commit:** `feat(rbac): user_roles hierarchy schema and RLS`

### Phase 2: Granular Permission Checkboxes
- `user_permissions` table: `user_id`, `capability` (e.g. `edit_terms`, `moderate_chat_platform_wide`, `manage_admins`), boolean-effectively via row existence. This is the "simple checkbox for that user" layer.
- RLS + a helper function/view combining `user_roles` + `user_permissions` so the rest of the app can ask one question ("can this user do X?") instead of checking tier and permissions separately everywhere.
- **Commit:** `feat(rbac): granular per-user permission grants`

### Phase 3: Permitted Admin ↔ Organization Ownership
- Wire `permitted_admin` role rows to be created/removed automatically when someone becomes an org owner/co-owner (via the existing `OrgAffiliationRequestModel`/org-management flow), rather than needing manual admin action every time an org changes hands.
- **Commit:** `feat(rbac): auto-derive Permitted Admin from organization ownership`

**Checkpoint 1 notes (see ADR-007 in `Core_files/decisions.md`):** `permitted_admin`/`user` map onto the v0.5 schema's existing `org_owner`/`org_co_owner`/no-row shape rather than a renamed enum, so no extra migration round was needed. `org_owner` now auto-derives from `organizations.owner_profile_id`; `org_co_owner` does not, since no co-owner concept exists anywhere in the schema or app yet — Checkpoint 2/3 need to design that designation mechanism before it can auto-derive. `user_permissions` writes are currently master_admin-only (the roadmap's "Admin, if permitted to" delegation is deferred to Checkpoint 2's permission-management UI).

## Checkpoint 2 — Admin Hub Rebuilt on Real Backend ✅ Complete (2026-08-23)

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Replace Client-Side Checks
- Replace every remaining `provider.isAdminUser`-style client check in `AdminHubScreen` and `GoRouter` with real Supabase role lookups (should mostly already be true after v0.5 Checkpoint 2 — this phase is the "confirm it, add the new Admin/Permitted Admin tiers on top" pass, not a redo).
- **Commit:** `refactor(admin): AdminHubScreen enforces real tiered roles`

### Phase 2: Batch Actions
- Multi-select in the broadcaster verification queue for bulk approve/reject — the one item the audit found genuinely missing (filtering itself already existed).
- **Commit:** `feat(admin): batch actions in verification queue`

### Phase 3: Permission-Management UI
- A screen (Master Admin only) to view all Admins/Permitted Admins, promote/demote, and toggle the Checkpoint 1 Phase 2 capability checkboxes per user.
- **Commit:** `feat(admin): role and permission management UI`

**Checkpoint 2 notes:** the `/admin` route guard and `AdminHubScreen`'s access check were already RPC-backed (no leftover email-allowlist checks) — Phase 1's real work was adding `isMasterAdmin` (via `is_master_admin()`) so the UI can tell Master Admin apart from plain Admin, on top of the existing `isAdminUser`. Batch actions (Phase 2) loop the existing single-item approve/reject methods rather than a bulk SQL update, so org/streamer-profile creation and notifications still fire per application. The new "Roles & Permissions" tab (Phase 3) is Master-Admin-only UX gating — write access is enforced server-side by Checkpoint 1's master_admin-only RLS regardless. It can grant/revoke `master_admin`/`admin` and toggle capability checkboxes; `org_owner`/`org_co_owner` rows are listed/revocable but not grantable here, consistent with ADR-007 (Permitted Admin stays auto-derived from organization ownership, not ad-hoc grants).

## Checkpoint 3 — Org-Scoped Tools for Permitted Admins ✅ Complete (2026-08-23)

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Scope `OrgManagementView` to Permitted Admin
- Org Owners/Co-Owners get an admin surface reusing the existing `OrgManagementView`, scoped by RLS so they only ever see/manage their own organization — not the platform-wide admin view.
- **Commit:** `feat(admin): org-scoped management surface for Permitted Admins`

**Checkpoint 3 notes:** new `/org-admin` route + `OrgAdminScreen`, reusing `OrgManagementView` pinned to `AppProvider.permittedAdminOrgIds` (resolved from the signed-in user's own `user_roles` rows — RLS already lets any signed-in user read those without admin tier). The route/screen scoping is UX convenience, not the security boundary: `org_venues`/`org_speakers`/`affiliation_requests` RLS already restricts writes to the real owner/co-owner regardless of what org id a client asks for. Surfaced and fixed a latent gap along the way: `ensureOrgDataLoaded` only ever found an org in the in-memory mock `_streamers` list, so a Permitted Admin returning on a fresh session would hit "Organization not found" for their own real org — it now seeds `_streamers` from the real `organizations` table when missing. `OrgManagementView` also gained a `showAuditTrail` flag (off for Permitted Admins), since `audit_logs` stays admin-tier-only at the RLS layer and would otherwise show an always-empty tab.

## Checkpoint 4 — Platform-Wide Chat Moderation Tools ✅ Complete (2026-08-23)

**🚀 Checkpoint kickoff:** push to GitHub.
**🧹 Optional polish session:** good checkpoint to end a version on with a security-focused pass — specifically try to access Admin/Master-Admin-only surfaces as a lower-tier or unauthenticated user and confirm every attempt fails server-side, not just client-side.

### Phase 1: Chat Moderation Dashboard
- A view (Admin tier and above) surfacing reported messages from v0.6's `chat_reports` table, with resolve/dismiss/ban actions — this is the piece that was completely absent before (application-verification moderation existed; live-chat moderation didn't).
- **Commit:** `feat(admin): platform-wide chat moderation dashboard`

**Checkpoint 4 notes:** always-present "Chat Moderation" tab (admin-tier, not Master-Admin-only) lists `chat_reports` platform-wide with three resolve actions: Dismiss (deletes the report row — `chat_reports_delete_admin`, new in `20260827120000_chat_reports_admin_resolution.sql`, since v0.6 shipped that table with no UPDATE/DELETE policy on purpose), Delete Message (deletes the `chat_messages` row, which propagates to every viewer's live chat via the existing `postgres_changes` DELETE event `LiveChatController._handleDelete` already handles — no new realtime wiring needed — and cascades to remove every report on that message), and Mute/Ban Sender (inserts into `chat_muted_users`, enforced by the existing insert policy that rejects muted senders). **Security verification (the checkpoint's optional polish item, done as part of Phase 1 rather than a separate pass):** read every relevant RLS policy (`chat_reports`/`chat_messages`/`chat_muted_users`, all `to authenticated` + `is_admin_tier()`-or-`owns_stream()` gated — anon has zero matching policies, so it's blocked at the Postgres role level regardless of app logic) and ran `npx supabase db advisors --linked --type security` against the live remote project: zero findings against these three tables (the linter flags missing/overly-permissive RLS by default; its silence here is corroborating evidence, not just the migration text). The advisor did surface pre-existing, out-of-scope findings unrelated to chat moderation — several `SECURITY DEFINER` helper functions (`is_admin_tier`, `has_permission`, `chat_is_muted`, `log_audit_event`, etc.) are callable by `anon`/`authenticated` beyond their explicit grants, which for boolean self-checks is by design but for `log_audit_event`/`bootstrap_admin_role` is worth a dedicated look later — noted here, not fixed in this checkpoint.
