# v0.8 — Admin Upgrade (Tiered RBAC)

**Why this version exists:** "Upgrading the admins" — replacing the flat "3 hardcoded emails = super admin" model with a real hierarchy, now that v0.5 gives us a real backend to enforce it and v0.6 gives admins something new to moderate.

**The hierarchy, as you specified it:**
1. **Master Admin** — top tier. Can grant the Master Admin role to others (so there can be multiple Master Admins — this is the "goes back to where I work" case, e.g. co-founders/trusted leads). Unrestricted platform control.
2. **Admin** — appointed by a Master Admin. Day-to-day moderation/verification powers; cannot grant Master Admin or Admin roles to others (only a Master Admin can).
3. **Permitted Admin** — for Organization Owners and Co-Owners specifically. Scoped to their own organization only, not platform-wide.
4. **Checkbox-style granular grants** — layered on top of any tier above: a Master Admin (or an Admin, if permitted to) can tick specific extra capability checkboxes for a given user, independent of their base tier (e.g. "can also edit platform Terms & Conditions" for a specific Admin who wouldn't otherwise have that).

**Depends on:** v0.5 (the `user_roles`/`user_permissions` tables were already scaffolded there specifically so this version doesn't need another schema migration round).

## Checkpoint 1 — Roles & Permissions Data Model

**🚀 Checkpoint kickoff:** push to GitHub.

### Phase 1: Role Hierarchy Schema
- Finalize the `user_roles` table: `role` enum (`master_admin`, `admin`, `permitted_admin`, `user`), `granted_by` (references the granting user, for audit trail), `org_id` (nullable — only set for `permitted_admin`, scoping it to one organization).
- RLS: a `master_admin` can insert/update any row; an `admin` can only insert/update rows for `user`-tier accounts (i.e. can't self-promote or promote others to admin/master_admin); `permitted_admin` rows can only be set by a `master_admin`/`admin` or derived automatically from organization ownership (see Phase 3).
- **Commit:** `feat(rbac): user_roles hierarchy schema and RLS`

### Phase 2: Granular Permission Checkboxes
- `user_permissions` table: `user_id`, `capability` (e.g. `edit_terms`, `moderate_chat_platform_wide`, `manage_admins`), boolean-effectively via row existence. This is the "simple checkbox for that user" layer.
- RLS + a helper function/view combining `user_roles` + `user_permissions` so the rest of the app can ask one question ("can this user do X?") instead of checking tier and permissions separately everywhere.
- **Commit:** `feat(rbac): granular per-user permission grants`

### Phase 3: Permitted Admin ↔ Organization Ownership
- Wire `permitted_admin` role rows to be created/removed automatically when someone becomes an org owner/co-owner (via the existing `OrgAffiliationRequestModel`/org-management flow), rather than needing manual admin action every time an org changes hands.
- **Commit:** `feat(rbac): auto-derive Permitted Admin from organization ownership`
