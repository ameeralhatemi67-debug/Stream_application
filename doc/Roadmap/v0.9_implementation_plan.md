# Implementation Plan — Version 0.9 (Settings, Legal, Deletion)

This plan outlines the design and implementation details for Version 0.9 of the Streamer App, focusing on Settings Screen Cleanup, App Store/Play Store compliant Account & Data Deletion, and Saudi Personal Data Protection Law (PDPL) Consent tracking.

---

## Technical Design & Database Schema Changes

### 1. Account & Data Deletion (Cascading & DB Integrity)
The current database schema restricts deletion of a `profiles` record if the user owns an organization:
- `organizations.owner_profile_id` references `profiles.id` with `on delete restrict`.

To allow clean account deletion from the client side without throwing foreign key errors, we will introduce a PostgreSQL trigger function that intercepts profile deletion and automatically cleans up owned organizations.

```sql
-- Migration file: supabase/migrations/20260829000000_account_deletion_cascades.sql

-- 1. Create a trigger function to handle dependencies before profile deletion
create or replace function public.handle_profile_before_delete()
returns trigger
security definer -- Runs with elevated privileges to clean up dependent records
language plpgsql
as $$
begin
  -- Delete organizations owned by this user (this will cascade to org_venues and org_speakers)
  delete from public.organizations where owner_profile_id = old.id;
  
  -- Anonymize chat messages instead of hard-deleting to preserve chat flow context for other viewers
  update public.chat_messages 
  set 
    sender_name_en = 'Deleted User',
    sender_name_ar = 'مستخدم محذوف',
    message_text = 'This message was deleted'
  where sender_profile_id = old.id;

  return old;
end;
$$;

-- 2. Bind the trigger to the profiles table
create trigger tr_profiles_before_delete
  before delete on public.profiles
  for each row
  execute function public.handle_profile_before_delete();
```

### 2. PDPL Consent Tracking
To comply with the Saudi Personal Data Protection Law (PDPL), we will add fields to the `profiles` table to record when the user explicitly accepted the Privacy Policy and Terms of Service.

```sql
-- Migration file: supabase/migrations/20260829000100_pdpl_consent_tracking.sql

alter table public.profiles
  add column consent_version text,
  add column consent_accepted_at timestamptz;
  
comment on column public.profiles.consent_version is 'The version of the privacy policy accepted by the user (e.g., v1.0).';
comment on column public.profiles.consent_accepted_at is 'The timestamp when the user explicitly gave consent during onboarding.';
```

- **Conditional Rendering**: Group remaining settings into cards and render dynamically depending on user role:
  - *Viewer*: Profile info, Language, Theme, Privacy, Legal, and "Delete Account".
  - *Streamer*: Viewer settings + Streaming output resolution and audio bitrate defaults.
  - *Org Owner*: Streamer settings + Organization branding and speaker roster management shortcuts.
- **Account Deletion Flow**: Add a "Delete My Account" button. When tapped, it displays a confirmation dialog warning that this action is permanent and deletes all personal data. On confirmation, it deletes the user's account using the Supabase auth client:
  ```dart
  await supabase.auth.admin.deleteUser(currentUserId); // Or via an RPC function call if RLS prevents client-side deletion
  ```
  *(Note: Since client-side auth.deleteUser is restricted, we will expose a secure PostgreSQL function `public.delete_own_account()` that regular users can invoke via RPC to delete themselves).*

## Verification Plan

### Automated Checks
- Run `supabase db lint` to check SQL migrations.
- Run `flutter analyze` to ensure code changes in `settings_screen.dart` compile correctly.

### Manual Verification
1. **Account Deletion**:
   - Register a dummy streamer account, create an organization, post a chat message, and then trigger the "Delete Account" flow.
   - Verify that:
     - The organization is successfully deleted (verifying the trigger).
     - The chat message is anonymized (sender name changes to "Deleted User").
     - The user is logged out and the Auth user is completely deleted from Supabase.
2. **PDPL Consent**:
   - Log in as a new user and ensure registration blocks until the consent dialog is accepted. Verify that `consent_version` and `consent_accepted_at` are correctly written to the Database.
